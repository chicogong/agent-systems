# DSH：基于插件注入的并发工具池与按序提交关口

[返回系统目录](../README.md) · [关键代码导读](code-walkthrough.md)

当大模型在一次回复里一口气开出三张工具工单——`A` 是全仓全文检索（耗时 3 秒），`B` 是读取配置文件（耗时 20 毫秒），`C` 是读取 `package.json`（耗时 15 毫秒）——运行时立刻面临一个两难抉择：如果老老实实串行排队，`B` 和 `C` 就得陪着慢吞吞的 `A` 白等 3 秒；可如果直接用 `Promise.all` 谁先跑完谁先入账，事件流与历史账本的顺序就会彻底乱套，甚至在无界面的后台 SDK 环境里，因为没人挂载审批弹窗而让危险调用失控裸奔。

DeepSeek 开源的 **DeepSeek Harness**（简称 DSH）给出了两个极具工程美感的设计回答：在架构组装层，用 **Cordis 插件与服务注入**让审批、沙箱、文件系统按需插拔且缺省安全；在工具调度层，把**单批工具执行完成**与**向模型提交结果**拆成两道独立关口——执行过程允许重叠抢跑，结果落账严格按序放行。

## Cordis 服务注入：为什么不把能力写死在循环里

如果还没熟悉基础的[Agent loop](../../concepts/agent-loop.md)，可以把 Harness 理解成让大模型持续干活的「运行底盘」。与 [Pi](../pi/README.md) 按上下游纵向切成三个固定包的思路不同，DSH 基于插件框架 **Cordis** 把整个运行时拆成横向的服务总线：模型会话、工具注册表、用户审批、文件系统和子进程执行器全都是可替换的插件服务。

| 服务切面 | 插件化组装方式 | 解决的工程问题 |
| --- | --- | --- |
| **宿主装配** | 用 Cordis 组织插件，通过配置方案（`profile`）与组合包（`bundle`）按需拼装，后台集成可只引精简版 `sdk-minimal` | 同一套核心循环既能长出全功能交互应用，也能裁成无 UI 的轻量嵌入式运行器 |
| **工具生命周期** | 将准备、守卫（guard）、审批询问、执行与后处理拆为独立扩展点 | 让权限拦截与参数预处理在真正派发工具前统一收口，不必塞进每个工具内部重复实现 |
| **底层执行环境** | 注入统一的文件系统服务、子进程服务与 `bash-sandbox` 执行器 | 所有工具共享同一套宿主边界，按当次策略决定命令可触达的文件与系统资源 |

上述服务边界见官方[架构说明](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/architecture.md#L11-L35)与[文件系统、子进程服务说明](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/architecture.md#L119-L137)。这种依赖注入设计最妙的地方在于**服务缺失时的默认防御**：假如你在服务端用 `sdk-minimal` 跑批处理任务，根本没加载交互审批 UI 插件，此时一旦某个工具触发了「需询问用户（`ask`）」规则，系统不会傻等卡死，更不会糊涂放行，而是因找不到审批服务直接判定为**拒绝**。

## 乱序跑完、顺序交卷：拆开「执行完成」与「结果提交」

回到开头的 `A`、`B`、`C` 三个工具调用。DSH 在单批调度里引入了一个和 TCP 乱序重排缓冲区（Reorder Buffer）异曲同工的机制：

![工具执行可以重叠，事件结果仍按调用序列提交](../../../figures/dsh-tool-batch/diagram.svg)

[图源](../../../figures/dsh-tool-batch/scene.excalidraw) · [PNG 预览](../../../figures/dsh-tool-batch/preview.png) · [不看图的说明](../../../figures/dsh-tool-batch/README.md)

整个批次在有界并发池（Bounded Pool）中推进：

1. **按序准入与重叠执行**：`A`、`B`、`C` 依次通过前置检查与许可判定；只要都支持并行且没顶到并发池上限，三者几乎同时开始执行。
2. **先跑完的先在槽位候场**：`B` 和 `C` 在几十毫秒内率先拿到结果，状态变为就绪（`ready`），但它们**不能越过还没跑完的 `A` 抢先向外发完成事件或写入结果流**。
3. **游标推进批量放行**：负责把关的提交器 `commitReady()` 死死盯住当前队头槽位 `A`；直到第 3 秒 `A` 终于跑完就绪，`commitReady()` 才一次性顺序吐出 `A → B → C` 三份结果（完整函数链路见[关键代码导读](code-walkthrough.md)）。

为什么要故意让快工具等慢工具？因为大模型接口、前端流式组件以及事后回放日志都高度依赖「第 `i` 个工具调用对应第 `i` 条结果事件」的确定性序列。DSH 用轻微的**队头阻塞（Head-of-Line Blocking）延迟可见性**，换来了并发提速与确定性事件序的兼得。但工程师心里必须留一根弦：**排好序的只是交回给模型的回执**——如果 `B` 修改了外部数据库或磁盘文件，那个真实世界的副作用早在第 20 毫秒就已经发生了。

## 两条不可逾越的安全红线

阅读或接入 DSH 时，有两处安全开关直接决定防线是否生效：

- **缺省拒绝的审批门禁**：任何返回 `ask` 的工具调用都必须向审批服务拿到显式放行回执；服务未注册、上下文缺失或用户取消一律按拒绝落定，且高优先级的守卫（`guard`）拒绝不可被其他钩子的 `allow` 覆盖。
- **策略驱动的沙箱边界**：`bash-sandbox` 执行器并非无条件隔离——一旦策略被设为 `danger-full-access`，它会直接走无限制的基础子进程执行；而在启用受限策略时，若当前系统缺少可用沙箱后端，执行器会直接报错而不会偷偷降级成裸跑。此外，上游 [SAFETY.md](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/SAFETY.md) 明确提醒该开发者预览版尚未经过完整安全审计，面对不可信代码时仍需额外部署外部容器或虚拟机隔离。
