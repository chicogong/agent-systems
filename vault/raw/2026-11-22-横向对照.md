# 横向对照

[返回首页](../../README.md)

只读一个开源 Agent 项目的源码时，你很容易产生一种错觉：作者这样写循环、这样存会话、这样拦命令，似乎就是“唯一自然”的做法。直到线上真正踩了坑——用户在工具执行中途插话把消息序列搞崩、明明写进磁盘的规则下一轮却像失忆一样失效、部署请求超时后自动重试闯出双倍事故——再去翻第二、第三套源码，你才会恍然大悟：**每一个看似不起眼的队列、状态拆分或对账步骤，背后都在回答同一个问题——每多要一分确定性，你愿意付出多少架构复杂度**？

这组横向对照专门做这件事：每次抓准一个真实的工程两难，把它同时摆在多套代表性源码面前，拆解各自的控制流、数据结构与取舍代价。

## 这组文章围绕的四条主线

1. **运行循环**（Agent loop）：模型只负责提出下一步动作提案；真正拍板“继续下一轮、塞入新指令、退避重试还是立即停机”的，是宿主循环里的闸口逻辑。
2. **上下文与状态**（Context & State）：模型是无状态函数，只看得见**本次请求载荷里的字节**。把“存下来”变成“用得上”，中间隔着分支投影、检索筛选与提示重编译。
3. **权限、隔离与恢复**（Permission & Recovery）：审批管“准不准做”，沙箱管“进程能碰哪”，而跨网络副作用一旦超时，必须靠稳定操作 ID 与远端对账收尾。
4. **完成与证据**（Completion & Evidence）：循环正常退出只代表“程序不跑了”，唯有文件改动、测试回执与边界记录三者闭环，才能交付给人类验收。

初读时不必从头按顺序啃完：直接挑最戳中你手头问题的那一篇，先顺着配图和数据流看懂设计权衡，需要深挖实现细节时再点开文末的固定源码行号。

## 来源与边界

本组对照基于各篇注明的固定 Git 提交（静态源码路径核对）与官方公开技术文档编写，重点拆解不同系统在控制流、状态结构与安全边界上的架构取舍。文中未对多套系统做同一机器、同一任务集下的横向跑分或完成率排名；涉及闭源产品的部分仅对比用户可配置、可观测的公开接口行为，不臆测未公开的内部实现。
