# 动手：按原操作 ID 找回回执

[返回学习路线](../learning-path.md) · [审批与恢复的机制对照](../comparisons/permission-and-recovery.md) · [第一次本地练习](first-agent-loop.md)

## 3 分钟显微镜：跑完这几行，你会亲眼看到什么？

很多 Agent 教程在教错误处理时，会轻描淡写写一句 `except Exception: retry()`。一旦你的工具干的是发版本、扣余额、建工单这类外部写操作，这行看似无害的重试就是定时炸弹。

在这个零依赖的 3 分钟小实验里，程序同时为你打开了两个视角——**客户端手里的回执**与**服务端底账里的真实副作用计数**（`effects`）。跑完下面几行命令，你会亲眼看到三幕极具冲击力的反差：

1. **回执明明为空，服务端副作用计数却已经是 1**（`receipt=null` 但 `effects=1`）：发版请求 `publish-v1` 其实早已在服务端登记成功，只是回程答复丢了——在客户端眼里风平浪静，在外部世界里大局已定。
2. **最诚实的高手敢于停在 `unknown_stop`**：当回执丢了、目标服务又没有查询接口时，宿主在 `no_lookup` 模式下果断刹车，绝不赌运气盲目重发（此时上帝视角显示 `effects=1`，而宿主诚实承认自己不知道）。
3. **自作聪明换个新 ID 重试，当场制造双倍事故**：在 `unsafe_new_id` 模式下，客户端给重试请求换了个带 `-retry` 后缀的新编号，直接绕过服务端去重防线，把发布副作用从 `1` 翻倍成了 `2`！

在看输出前先对齐三个核心词：**操作 ID**（`operation_id=task-42:publish-v1`，发送前由宿主生成的唯一业务标识）、**回执**（服务端返回的 `accepted` 答复）、**对账**（回执丢失后按原 ID 查询真实状态）。仅需 Python 3.10+ 标准库，不联网、不发真实请求。

## 第一步：一口气跑完四种命运对照

在仓库根目录执行四条模式命令与单元测试：

```bash
python3 examples/remote-effect/demo.py --mode normal
python3 examples/remote-effect/demo.py --mode lost_receipt
python3 examples/remote-effect/demo.py --mode no_lookup
python3 examples/remote-effect/demo.py --mode unsafe_new_id
python3 -m unittest discover -s examples/remote-effect -p 'test_*.py'
```

把四种路径下“宿主手里看到的证据”和“上帝视角的真实副作用数 `effects`”摆在一起对比：

| 运行模式 | 宿主拿到了什么证据 | 宿主的下一步动作 | 服务端真实副作用数 `effects` |
| --- | --- | --- | --- |
| `normal` | 发送后直接收到 `accepted` 回执 | 确认完成并收口 | `1` |
| `lost_receipt` | 发送回执为 `null`；随即拿原 `operation_id` 查回 `accepted` | 凭查询证据确认完成，**不再补发写入** | `1` |
| `no_lookup` | 发送回执为 `null`；目标服务不支持查询 | 停在 `unknown_stop`，交由人工对账 | `1`（注意：宿主此刻**并不知道**是 0 还是 1） |
| `unsafe_new_id` | 回执为 `null`；明明查到了原记录，却仍换新 ID 重发 | 绕过幂等保护，错误制造第二次写入 | `2` |

重点盯住 `no_lookup` 这一行：JSON 里的 `"effects": 1` 是教学模拟器为了让你看清真相而特意附上的“场外裁判读数”；真实的宿主代码只能看到 `receipt=null` 和 `lookup=unavailable`。在信息不全时刹停在 `unknown_stop`，恰恰是防止故障扩大的关键工程素养。

## 第二步：把 `lost_receipt` 与 `unsafe_new_id` 的分岔点揪出来

为什么同样经历了第一次丢回执（`receipt=null`），一个稳稳收在 `1` 次操作，另一个却闯出 `2` 次祸？顺着 `events` 数组逐条比对就能抓到精确的分水岭：

| 事件顺序 | 关键字段特征 | 在系统里发生了什么 |
| --- | --- | --- |
| 第 1 步：初次提交 | `event=submit`，携带原 `operation_id`，`receipt=null` | 服务端已落账，但答复在半路丢失，两边起点完全相同 |
| 第 2 步：按原号对账 | `event=lookup, result=accepted` | 宿主拿着发送前记下的原 `operation_id` 查明：操作早已生效（`lost_receipt` 到此安全收工！） |
| 第 3 步：换号硬试（反例） | `event=unsafe_retry`，ID 变成 `...-retry`，`receipt=accepted` | 换了新 ID 后，服务端把它当成一次全新的发布请求照单全收，副作用喜加一 |

## 第三步：打开源码看清三处关键设计

翻开 [`demo.py`](../../examples/remote-effect/demo.py)，核心逻辑只有短短三处：

1. **发前定号**：`run()` 在调用提交接口**之前**就先固定了 `operation_id`。如果每次捕获异常都在循环里 `uuid4()` 现捏一个新号，服务端神仙难救。
2. **先落账、后回执的真实故障点**：`FakeService.submit()` 先把操作写进内部字典 `operations`，然后才根据故障模式决定返回回执还是返回 `None`。这精准复刻了“服务端事务已提交，响应报文断在回程”的经典线上故障。
3. **幂等承诺在服务端，不在客户端一厢情愿**：本例中只有 `FakeService` 明确实现了按同一 `operation_id` 去重；对接真实第三方 API 时，必须先查清对方文档是否支持幂等键、有效期多长、查询接口有没有延迟。

## 来源与边界

本实验在单进程内存中模拟“回执丢失与原号对账”，暂未引入真实网络套接字超时、读写分离查询滞后（查的时候还是 404，刚放弃它却落盘了）以及多线程并发竞争。想亲眼观察真实本机 TCP/HTTP 超时与上述两种极具迷惑性的“假 404”，请直接进入进阶篇 [HTTP 回执实验](http-receipt.md)；想对照开源框架源码怎样管理本地进度，请读[四系统恢复对照](../comparisons/permission-and-recovery.md)。
