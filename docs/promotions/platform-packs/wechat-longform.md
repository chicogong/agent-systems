### 一觉醒来，30 步任务花掉了 90 万 Token？

很多研发团队第一次把自动化编码或多步调研 Agent 推上生产时，都会经历一次“账单惊魂”：

明明模型每一步只输出了几十个 Token 的工具调用参数，整个任务跑下来也就 30 步，但在月末拉出账单一看，累计消耗的输入 Token 居然逼近 **100 万**；而且每一步模型吐第一个字（TTFT，Time to First Token）都要卡顿好几秒。

翻开工程代码排查，大家往往会发现一个令人哭笑不得的事实——罪魁祸首既不是模型变笨了，也不是业务逻辑写错了，而是一行看似非常职业的“良好习惯写法”：

> 有人在 System Prompt 的第一行顺手拼了句：  
> `当前系统时间：2026-11-26 15:30:00`；  
> 或者在对话轮次过多时，写了句看似优雅的滑动窗口：`messages.pop(0)`。

在单轮对话或短聊天机器人里，这种写法人畜无害；但在多步运行的 Agent 循环里，它会瞬间废掉现代大模型底座最核心的一项降本红利——**KV 前缀缓存（Prefix Caching）**。

### 一、 账单暴涨背后的物理现实：100:1 的输入输出倒挂

要理解为什么一行时间戳会摧毁系统性能，我们必须先看清 Agent 循环与普通 Chat 对话的根本差异。

普通问答一问一答，输入与输出长度比例大致在 `2:1` 到 `5:1` 之间。但 Agent 是一个围绕**工具反馈闭环运转的状态机**：

> 💡 **核心机制**：  
> 每次模型执行完一次 Bash 命令、读完一个代码文件，宿主程序（Harness）都必须把 **系统提示词 + 全部工具 Schema 声明 + 之前所有轮次的对话与执行结果 + 刚刚拿到的一小段新观察**，打包成一个全新的超长数组，再次发给大模型。

![前缀缓存命中与雪崩失效对比](https://cdn.jsdelivr.net/gh/chicogong/agent-systems@main/figures/prefix-cache-mechanics/preview.png)

我们来算一笔真实的账：
- 假设基础 System Prompt 与工具声明占 `6,000` Token；
- 每一步新增工具执行结果（观察）与模型思考共 `1,000` Token；
- 连续执行 25 步任务：
  - 模型实际生成的输出总和只有约 `3,000 ~ 5,000` Token；
  - 但 25 次请求累计发送给模型的输入总量高达：  
    $$\sum_{k=1}^{25} (6000 + 1000k) = 475,000 \text{ Tokens}$$

**输入与输出 Token 呈现极其恐怖的 100:1 悬殊倒挂！**

现代推理引擎（如 Anthropic、OpenAI、vLLM、SGLang）之所以能够支撑这种高频调用，核心依靠 **Transformer 因果注意力的前缀缓存（KV Cache）**。只要本次请求的前缀 Token 与显存中已存的缓存**从左往右逐字节严格匹配**，引擎就能跳过前面几万 Token 的注意力计算，带来 **50% 至 90% 的计费折扣**，并将首字生成延迟压至毫秒级。

**然而物理法则极其残酷：前缀匹配是从左至右严格逐块比对的。哪怕第 1 个 Token 里变了一个毫秒数字，后方整整几万 Token 的缓存瞬间全盘击穿！**

### 二、 线上排查必看：摧毁缓存的四大反模式

在审查真实工业级 Agent 系统的故障日志时，我们发现九成以上的性能事故与成本失控，都源自这四大反模式：

> ⚠️ **高危反模式清单**：
> 1. **在 System Prompt 首部塞入秒级时间戳或动态 Request ID**  
>    每次请求的前缀第一行都在变，后方几万字的核心规则与工具定义每一步命中率都是 0%；
> 2. **每一步无序增删或动态加载 `tools` 声明**  
>    工具 Schema 紧贴系统提示之后。如果使用 Python 字典无序遍历，或者每轮根据猜想动态插拔工具，会导致整个前缀哈希全部被打碎；
> 3. **逐条剔除旧消息的滑动窗口（`pop(0)`）**  
>    为了控制上下文长度，顺手把列表第一项删掉。这会导致后续所有消息在序列中的绝对位置整体前移一位，导致所有词元的相对位置编码改变，缓存直接作废；
> 4. **工具返回 JSON 的键名未排序（Unsorted Dict Keys）**  
>    未配置 `sort_keys=True`，相同字段在序列化为字符串时顺序飘忽不定。

针对上述痛点，生产级 Harness 只有一条铁律——**越稳定、跨步越不变的内容越靠左（靠前）；越鲜活、每步都在变的内容越靠右（靠后）**：

> 📌 **五层稳定度递减黄金排版律**：
> - **Level 1 [全局恒定]**：系统角色准则 + 字母严格排序的稳定 Tool Schemas（命中率 95%+）；
> - **Level 2 [会话级稳定]**：项目协作规范（如 `AGENTS.md`）+ 会话全局核心约束；
> - **Level 3 [阶段级稳定]**：达到 80% 水位线后一次性生成的定态阶段性摘要块；
> - **Level 4 [步级纯追加]**：一轮接一轮向后追加的历史消息（Append-Only，绝不回头篡改修改既往消息）；
> - **Level 5 [瞬态队尾]**：确需秒级时钟或单步剩余步数提醒，作为增量观察挂在最末端。

### 三、 为什么千万不能让你的 Agent 自己汇报“我做完了”？

除了 Token 账单暴涨，另一个常见事故是**模型汇报假完成**。

很多开发者写完一个能够调用终端的 Agent，给模型的终结指令往往是：“完成任务后，请输出 `DONE` 或调用 `finish_task`”。

结果在真实场景中经常出现灾难性场面：
- 模型在修改生产配置文件时把参数改错了，导致语法校验失败；
- 但因为写文件工具成功向磁盘写入了内容，工具底层返回了 `{"status": 200, "ok": true}`；
- 模型看到工具返回了 `ok`，欣喜若狂地向用户汇报：“报告主人，配置文件已成功更新并测试完毕！”

> ⚠️ **生产警示**：  
> **工具调用成功 ≠ 业务目标达成！** 永远不要把“模型宣称自己做完了”当成任务验收的标准。

![Agent 运行循环与宿主门禁](https://cdn.jsdelivr.net/gh/chicogong/agent-systems@main/figures/agent-loop/preview.png)

在真正的工业级 Agent 架构中，整个生命周期必须像现代编译器一样严格划分：

```
[用户目标] 
   ↓
1. 提案 (Propose)   ── 模型生成调用计划与参数
   ↓
2. 审批 (Approve)   ── 宿主安全策略拦截高危操作（如 rm -rf、转账）
   ↓
3. 执行 (Execute)   ── 沙箱子进程或隔离容器真实跑动
   ↓
4. 独立验收 (Host Gate) ── 宿主外壳主动读盘、运行单元测试，核验事实证据！
```

只有当**宿主程序自己运行的测试用例通过、编译退出码为 0、生成的输出文件通过了 Schema 验证**，宿主才允许状态机流转到结束状态。模型的意图只是“提案”，验收的裁判必须永远掌握在外壳手中！

### 四、 记忆与上下文的物理漏斗：“存了”不等于“看见了”

随着各家模型厂商宣布支持 100 万甚至 200 万超大上下文窗口，很多团队产生了一种虚假的幻觉：“既然窗口无限大，把所有历史、所有文件全塞进去不就解决记忆问题了吗？”

现实是残酷的：**简单检索（Retrieval）与多步链式推理（Multi-Step Reasoning）遵循截然不同的物理规律。**

![记忆与上下文漏斗](https://cdn.jsdelivr.net/gh/chicogong/agent-systems@main/figures/context-vs-memory/preview.png)

> 🔬 **工程现实中的四大层级漏斗**：
> 1. **物理存储（Stored）**：你把几万条规章制度存进了向量库或 SQLite；
> 2. **检索召回（Retrieved）**：检索器按照相似度找到了前 5 条关键事实；
> 3. **装配塞入（Assembled）**：当步骤预算只剩 200 Token 时，装配器因为塞不下整段文本，把排在第 1 位的安全禁令（“严禁在未获批准前推送到 master 分支”）直接截断丢弃；
> 4. **注意力吸收（Attended）**：即使塞进去了，Softmax 自回归注意力的权重总和恒等于 1。被几千行编译日志稀释后，有效信号密度不足 10%，模型直接发生近因偏置和“迷失在中间（Lost in the Middle）”。

**在真实工程中：存得好好的 ≠ 搜出来了 ≠ 塞进上下文了 ≠ 模型注意到了。**

## 🎯 读者自测：检验你的 Agent 系统直觉

在深入代码之前，不妨尝试回答以下三道生产一线测试题：

> **测验 1**：如果系统要求每步都向模型提供当前准确北京时间，如何在不破坏前缀缓存的前提下设计？  
> *提示：为什么不能放在 System Prompt 开头？作为只读 Tool 调用与作为 User 瞬态观察挂在队尾有什么本质区别？*

> **测验 2**：在上下文压缩时，为什么“每产生 1 条新消息就滑动 pop 掉最老 1 条”是极度业余的做法？工业级推荐的“水位线定态压缩”是如何工作的？

> **测验 3**：为什么说在多步 Agent 里，“超时重试”是极其危险的操作？对于涉及外部副作用（写库、部署、转账）的工具，超时后的第一原则为什么必须是“状态查询优先”？

如果你对上述问题的底层原理充满好奇，全书机制篇已经为你备齐了详尽的推导与实验脚本。
