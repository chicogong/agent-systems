# Pi 首篇实施计划

[返回路线](roadmap.md)

目标不是画一张“Pi 所有模块”巨图，而是让读者能回答：一条任务如何进入循环，工具调用与结果如何反馈，coding-agent 如何在核心之上加会话与资源，Extension 和 Skill 各自扩展什么。

## 内容架构

| 顺序 | 交付物 | 读者带走什么 | 证据门槛 |
| --- | --- | --- | --- |
| 1 | `docs/systems/pi/README.md` + 分层总图 | `pi-ai`、`pi-agent-core`、`pi-coding-agent` 的职责和边界 | 固定 commit 的包说明与源码入口 |
| 2 | `code-walkthrough.md` + 时序/状态图 | 从 `prompt()`、模型响应到工具结果及下一轮；何时结束 | 精确到函数、分支和事件的源码定位 |
| 3 | `extensions-and-skills.md` + 对比图 | Extension 的可执行扩展点与 Skill 的按需指令如何相互配合 | 官方文档与加载/调用实现均核对 |
| 4 | `sessions-and-context.md` | 内存消息、模型可见上下文、持久会话树与压缩的区别 | 明确代码路径、输入输出和未覆盖的模式 |
| 5 | `docs/comparisons/` 中第一张对照卡 | Pi 的取舍为什么与 Codex/OpenCode 不同 | 对照项目固定版本后再写，不提前猜测 |

每篇先给“30 秒读图”，再给关键代码逻辑的 5–10 步导读和固定源码链接，最后列边界、失败路径、术语和读者可自己验证的小练习。代码解释采用短伪代码或调用链，不大段搬运第三方源码。

当前已落地固定版本的分层图、运行代码导读和 Extensions/Skills 图文；它们属于**静态源码样章**。会话/上下文专章、失败路径演示、实际运行轨迹、跨项目对照和外部读者反馈仍待完成，不能把本轮产物称为正式发布版。

## 并行核对工单

- **运行时工单**：核对 `packages/agent` 的 loop、工具调用、steering/follow-up 与事件顺序；追到 coding-agent 的会话持久化边界。
- **扩展工单**：核对 Extensions 的加载与 API、Skills 的发现与按需读取、Pi Packages 的分发关系；找一个仓库自带的最小例子。
- **编辑与图稿工单**：整合前两项的固定版本证据，维护图源及导出、写读者视角的导读、复核图文是否说的是同一条路径。

这三项可以并行研究，但合稿时逐条检查箭头对应的证据。若来源冲突，先缩小图的范围，不用推断填空。

## 图稿与验收

Pi 首图沿用参考图的“分区卡片 + 清楚的连线标注 + Normal 标题/Code 节点”。原先首页的宽横向 Agent loop 保留为概念图，不冒充 Pi 源码图；Pi 图成为系统剖面入口。MCP 会强制换成 Excalifont，所以仓库 README 只嵌入由原生 `.excalidraw` 导出的 SVG；交互预览仅供编辑，不宣称字形一致。

完成一篇的最低验收：固定 commit；每个实现主张有定位；文字能脱离图独立阅读；PNG/SVG 与图源同源、无裁切；缩到 README 宽度可读；未知和未实测项明确标注。公开发布仍需许可证与外部读者复核。
