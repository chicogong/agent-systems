## 内容架构

本指南有两条相互链接的阅读路径：

1. **机制路径**：从 Agent loop 到工具、上下文、记忆、权限、恢复、多 Agent 与评测。先说明问题和设计空间，再画出常见的状态与数据流。
2. **系统路径**：在固定版本上研究真实开源项目，用统一模板记录入口、循环、工具、状态、上下文、控制和验证。只在有证据时把模块标到图上。

横向对照页回答“同一个机制为什么有不同实现”，不复制各项目剖面的全文。

### 读者路线与章节骨架

第一条是“从一次任务看完整生命周期”：目标和完成标准 → Agent loop → 工具调用与权限 → 结果验证 → 失败恢复。第二条是“状态如何延续”：消息与上下文装配 → 会话、截断与压缩 → 长期记忆与检索 → 跨任务复用。第三条是“把设计落到项目”：先看概念图，再进入固定版本的源码剖面，最后用横向对照理解取舍。三条路线互相链接，但不要求读者按项目名顺序阅读。

每个机制章节先回答一个具体问题，随后给出最小例子、主图、逐步解读、边界与反例、系统映射和可核对的来源。图既是导航，也是正文的一部分；不能用一张“总架构图”代替状态变化和失败路径。

| 机制主题 | 主图要回答的问题 | 优先连接的系统 |
| --- | --- | --- |
| Agent loop 与工具调用 | 模型何时决策、工具何时执行、结果怎样反馈？ | Pi、Codex、mini-SWE-agent |
| 上下文管理 | 本轮输入由谁装配，窗口不够时丢弃或压缩什么？ | Pi、Codex、OpenCode |
| 会话与长期记忆 | 当前任务历史、压缩摘要、跨任务记忆如何分层？ | Letta Code、Mem0、Pi |
| 权限与隔离 | 执行前在哪一层授权，风险操作怎样拦截？ | Codex、OpenHands、Cline |
| 恢复与验证 | 中断、工具失败或错误结果之后怎样重试和判定完成？ | OpenHands、mini-SWE-agent、Browser Use |
| 多 Agent 与委派 | 子任务怎样拆分、回收和对账，何时不值得委派？ | GPT Researcher、OpenClaw、Codex |
| 评测与可观测 | 怎样记录轨迹、复现环境并避免把测试通过当真实有效？ | 按可复现证据选例 |

表中的系统只是待核验的选题线索，不是已确认的实现归类。

## 首批范围

首篇从 **Pi** 起步；当前已有 12 个系统各一条固定源码路径的初稿，覆盖循环、工具、权限、浏览器行动、路由、记忆、checkpoint 与研究上下文。它们仍是**静态源码剖面**，不等于运行验证或公开预览已达标；完整清单见[系统目录](systems/README.md)。下一阶段应补真实运行轨迹、跨篇术语审稿和外部读者反馈，不因 Star 数直接决定文章深度。Pi 的具体工单见[首篇实施计划](pi-first.md)。

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| 样章 | Pi 的分层、关键循环、Extensions 与 Skills；补一篇 Agent loop 概念说明 | 每篇有可编辑图、文字版、固定来源与已核验代码路径 |
| 公开预览 | 权限、恢复、评测专题；OpenCode、OpenHands、mini-SWE-agent 剖面 | 两条阅读路径互通；图文经人工视觉复核；示例可运行 |
| 扩展 | Browser Use、OpenClaw、GPT Researcher、Qwen Code 等不同类型的 Agent；Aider、Cline、Goose、Gemini CLI 等对照卡 | 新系统能解释新的设计取舍，且来源版本与维护状态已核对 |

这不是完成清单。项目被列入候选不代表已完成调研或验证。

### 选题门槛与工作顺序

首篇先把 Pi 做成“读得懂且能跟源码”的剖面。Codex、OpenCode 随后用同一问题集对照；Letta 用于记忆专题。其他候选按差异补位：OpenHands 看执行环境和状态，mini-SWE-agent 看最小循环；浏览器、研究型和常驻型 Agent 只有在能提供新增机制案例时再进入正文。不要为了凑齐热门名单而牺牲深度。

单篇工作顺序：列问题和可能的误解 → 固定仓库版本 → 画粗粒度事实链 → 查源码/文档并标注证据等级 → 补全失败或停止路径 → 生成可编辑图及导出 → 文字版与视觉验收 → 交叉链接。若某段证据不足，把它留为“待确认”，不填进图的事实层。

### 近期可执行里程碑

1. **视觉样章**：让 Agent loop 图确立字体、颜色、标注和导出规范；请 1–2 位不熟悉 Agent 的读者只看图与文字版，指出哪里看不懂。
2. **最小机制链**：完成 Agent loop、工具权限、上下文装配三篇；每篇至少一张主图，必要时拆成状态变化图，不用超大一页图装下所有细节。
3. **系统切面**：先完成 Pi，再以 Codex、OpenCode 对照同一机制；记忆专题再引入 Letta。若对照不产生新的解释，就调整样本。
4. **公开预览**：完成链接、许可证、来源、图稿、移动端和外部读者复核，明确未完成章节；通过后才把私有筹备仓库转为公开。

## 每篇正式内容的验收

- 读者能从图中说出关键组件、动作方向与停止/失败路径；图中没有无出处的实现细节。
- `.excalidraw` 能重新导出 SVG/PNG，文字无裁切；交互画布若提供，也单独目视核对。
- 形式按[图稿设计原则](../figures/STYLE.md)选择；缩到 README 常见宽度仍能读，不能只在原尺寸下好看，也不能把所有章节画成同一套卡片。
- 源码结论带仓库、commit、文件/符号定位；运行结论附运行条件与结果。
- 图下有文字版，不依赖颜色表达唯一含义；专业词汇进入术语表。
- 原项目更名、迁移、归档或改变维护方向时，更新来源状态，不暗中把旧分析套到新版本。

## 发布门槛

公开前确定许可、审查私人内容与第三方材料、检查链接与图源、完成至少一轮外部读者反馈。发布后按固定版本维护剖面，新增项目先做候选卡，再决定是否深读。
