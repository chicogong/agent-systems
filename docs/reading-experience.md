# 阅读体验与读者路线

[返回首页](../README.md) · [当前进度与缺口](roadmap.md) · [写作与校稿方法](editorial-plan.md)

这份方案回答“怎样让不同背景的读者读懂同一套可靠内容”，不是新增一份书稿。**Markdown 仍是唯一正文**：GitHub、可携带 Markdown 包、PDF，以及可能的网站，都从它生成。书不应变成四份各自维护的内容。

## 先做好阅读路径，再决定站点

| 入口 | 当前角色 | 下一步 |
| --- | --- | --- |
| GitHub Markdown | 查源码、来源、图源与贡献；也是正文的权威地址。 | 保持可直接阅读，不让网站专有组件污染 Markdown。 |
| Markdown ZIP | 离线阅读，导入 Obsidian 或普通 Markdown 阅读器。 | 持续测试解压后图片、相对链接、首页与目录。 |
| PDF | 连贯阅读、固定页序与打印校稿。 | 每周审稿构建；完成实页与许可审查后才考虑正式版本。 |
| 静态阅读站 | 搜索、主题导航、读者路线、手机上的图文阅读。 | **先本地原型，不部署**；验证价值后再选公开托管。 |

不建议现在自研带账户、评论、进度同步的 Web 应用。它会引入登录、隐私、运维和第二套内容编辑流程，而当前最需要的是正文质量与图文可读性。也不把第三方阅读平台作为唯一入口：Obsidian Publish 需要通过 Obsidian 选择笔记发布，GitBook 的 Git Sync 是双向编辑；这些可以是日后的分发选项，却不能替代仓库源稿。[Obsidian Publish 操作说明](https://obsidian.md/help/publish/setup) · [GitBook Git Sync 说明](https://gitbook.com/docs/docs-as-code/git-sync)

本地站点原型优先试 **VitePress**：它直接以 Markdown 文件生成路由，并提供浏览器内全文搜索；不必重写当前章节。若试读证明需要更复杂的多语言、课程导航和开箱即用的文档组件，再评估 Starlight（默认使用 Pagefind 搜索）。这是当前仓库复杂度下的选型判断，不是两个框架的全面优劣结论。[VitePress Markdown 路由](https://vitepress.dev/guide/getting-started) · [VitePress 本地搜索](https://vitepress.dev/reference/default-theme-search) · [Starlight 搜索](https://starlight.astro.build/zh-cn/guides/site-search/)

原型应从当前正文和书稿清单生成导航与页面；封面、SVG/PNG、来源链接由同一批仓库资产提供。不复制正文到 `site/` 手工维护。先用 6–8 篇代表章节测试：入口与术语、一个机制、两个系统、一个对照、一篇代码导读，以及前言/阅读指南。检查中文搜索、移动端图宽与字体、相对链接、图的文字等价说明、无脚本时的基本阅读、构建产物中是否带入不该公开的文件。通过后再决定是否扩大到全书。

**公开部署是独立授权步骤。** GitHub 明确说明：GitHub Pages 站点即使源仓库为私有，也可能公开访问。因此目前不启用 Pages、不提交自动部署工作流；仓库公开、站点公开、PDF Release 要分别审批。[GitHub Pages 发布与可见性说明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

## 同一主题，三种进入深度

扩大读者群不意味着把每篇源码剖面写成高中教材。应以**同一事实链**提供不同入口，再在需要时向下钻：

| 路线 | 能带走什么 | 适合的表达 | 不强求 |
| --- | --- | --- | --- |
| 通识与零代码（高中生和非技术读者也可尝试） | 分清模型、Agent、工具和人的授权；理解“会回答”与“会执行”的差别。 | 生活化任务、短图、逐步动画/静态分镜、术语悬浮解释、风险提示。 | 一开始读具体函数与源码。 |
| 入门实践（大学生、转向 Agent 的开发者） | 搭一个小而可测的循环，解释状态、工具、上下文和失败恢复。 | 可运行的小实验、练习题、预期输出与检查点。 | 立刻理解所有框架与供应商。 |
| 工程与研究（正在构建系统的人） | 比较实现取舍，沿固定版本源码追踪关键路径，识别权限与可靠性边界。 | 代码导读、状态/时序图、失败分支、来源定位、横向对照。 | 把一个项目的局部路径误读为所有 Agent 的共性。 |

第一轮不新增三套平行正文。先为《Agent loop》《工具调用》《权限与审批》各做一个“通识引子 + 最小练习 + 深入源码”的入口页，三层都链接到现有章节；请真实读者分别试读并记录卡住的术语、图和步骤。高中生路线要控制对个人数据、付费账户与自动执行的风险，练习使用模拟文件和受控工具，不以年龄段承诺所有章节无门槛。

每篇正文可以逐步补“前置知识、读完能判断什么、一个常见误解、下一站”四项导航信息；导航元数据应放在清单或旁侧索引，不强制改动所有正文的 Markdown 语法。是否做交互练习，要看静态练习能否先解决理解问题。

## 闭源工具作为“使用与验证”案例

开源系统篇回答**代码怎样实现**；闭源工具篇只能回答**公开文档说明什么、在某版本界面下如何安全使用、产物怎样验证**。两者不能混在同一证据等级。可先选一个代表案例试写，比如用户所说的 WorkBuddy 若指腾讯 WorkBuddy：官方文档将其描述为面向办公任务的桌面 Agent，并区分默认权限与完全访问；这适合做“任务范围、授权确认、备份、结果校验”的教程，而不是推断其内部架构。[腾讯 WorkBuddy 概览](https://www.workbuddy.ai/docs/workbuddy/Overview) · [权限模式](https://www.workbuddy.ai/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Permission-Modes)

建议未来单设 `docs/tools/`，**不自动进入书稿清单**。一篇闭源工具指南至少记录：产品与页面版本/核对日期、官方文档链接、任务输入与样例数据、关键授权界面、产物核验方法、费用/隐私/地区限制、哪些行为亲自观察过、哪些只是厂商声明。截图须确认许可并遮蔽个人信息；界面变化时更新操作步骤，保留版本边界。可比较工具的**用户可见工作流**，不把 UI 体验倒推为源码事实。

后续候选可覆盖编码、办公、研究与浏览器任务各一类，但先用 WorkBuddy 或另一款工具完成一篇高质量样章，验证这种栏目确实帮助读者，而不是变成不断过时的工具清单。具体产品是否纳入由[选题地图](program.md)评估，首页只展示经复核的案例。

## 迭代顺序与验收

1. 修稳 PDF/Markdown CI，完成当前机制与项目篇的来源、图稿、可读性复核；这是所有新入口的底座。
2. 写三篇分层入口试稿和一篇闭源工具样章；先在 GitHub/Markdown 阅读包中请通识、学生和开发者读者各自走一遍。
3. 做**本地** VitePress 小样，不部署；比较“只用 GitHub 阅读”和“有导航、搜索的网站”是否明显改善找内容和看图。
4. 若原型有收益，再补站点构建与链接检查；公开前逐项审查许可、隐私、站点产物和访问权限，并另行决定是否开启 GitHub Pages 或其他托管。
5. 内容稳定后才考虑课程化、交互练习、进度记录等功能；优先保持无账户、静态、可下载的阅读方式。

成功指标不是网页数量，而是读者能找到正确路线、复述主图、追溯关键结论，并在真实任务中知道何时需要人来批准或验证。
