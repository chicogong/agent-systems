# 四种常被叫作“记忆”的状态

[返回横向对照](README.md) · [概念图：上下文与记忆](../concepts/context-vs-memory.md)

团队评审架构时，只要有人提一句“我们要给 Agent 加个记忆系统”，会议室里四个人脑海里浮现的往往是四件风马牛不相及的事：

- 交互设计师想的是：“用户关掉终端明天打开还能接着聊，而且改错方向时能退回第 5 步重开一条分支。”
- 产品经理想的是：“助手得长期维护一份项目说明书和用户画像，记住这人讨厌客套话、项目一律用 `pnpm`。”
- 搜索工程师想的是：“过去半年几千次对话里零散提过的客户偏好和历史故障，提问时能自动搜出最相关的三条塞进上下文。”
- 后端架构师真正睡不着觉的却是：“长流程跑到第 4 步卡在人工审批，半夜容器重启之后，怎么精确从第 4 步接着往下走，而不是把前 3 步再重跑一遍？”

在营销宣传里，这四件事全被笼统地贴上同一个标签——“Memory（记忆）”。但在系统工程里，**它们保存的对象、底层数据结构、读写延迟以及崩溃时的失效模式天差地别**。如果选错了型——比如拿向量数据库去存工作流执行进度，或者把几万条历史闲聊硬往常驻系统提示里塞——不用等上线，开发阶段就会陷入灾难。

本篇专门做一件事：**把笼统的“记忆”拆回四种精确的工程状态**，结合 [Pi](../systems/pi/README.md)、[Letta Code](../systems/letta/README.md)、[Mem0](../systems/mem0/README.md) 与 [LangGraph](../systems/langgraph/README.md) 的源码设计，给出一份可直接落地的架构选型指南。

## 先看本质差异：同一件事在四套系统里长什么样？

假设用户在一次发布任务里说：“以后生产环境发布一律走蓝绿切换；现在先停在待审批这一步。”在四套系统眼里，这句输入背后对应的状态切片完全不是同一种物种：

```text
1. 对话分支记录（Pi）       ──► JSONL 事件节点：{"id": "e8", "parentId": "e7", "role": "user", ...}
                                存的是「原汁原味的对话时间线与分叉历史」

2. 可编辑核心记忆（Letta）  ──► Markdown 文件：system/deploy_rules.md -> "- 生产发布默认采用蓝绿切换"
                                存的是「持续修订、常驻系统提示的活文档」

3. 可检索原子事实（Mem0）   ──► 向量条目：{"id": "mem_92", "memory": "生产环境发布一律采用蓝绿切换", "user_id": "u1"}
                                存的是「从对话提炼出来、按相关性语义召回的独立事实卡片」

4. 执行进度快照（LangGraph）──► 图状态快照：{"values": {"env": "prod"}, "next": ["human_approval"], "checkpoint_id": "..."}
                                存的是「状态机跑到哪一步、下一步该唤醒哪个节点的程序现场」
```

看清这四行数据结构，你就明白为什么它们根本不能互相替代。下面逐一拆解各自的账本结构、读写开销与致命边界。

## 四类状态的工程账本全解

| 维度 | [对话分支记录：Pi](../systems/pi/README.md) | [可编辑核心记忆文件：Letta Code](../systems/letta/README.md) | [可检索原子事实库：Mem0](../systems/mem0/README.md) | [执行进度快照：LangGraph](../systems/langgraph/README.md) |
| --- | --- | --- | --- | --- |
| **核心数据结构** | 追加式 JSONL 会话树（消息与分支事件构成父子链表） | 分层本地 Markdown 文件树（local MemFS v1 区分 `system/` 常驻区与按需读取区） | 提炼后的原子事实记录 + 向量索引（带 `user_id` / `agent_id` 等过滤元数据） | 绑定 `thread_id` / `namespace` / `checkpoint_id` 的图通道状态快照（`StateSnapshot`） |
| **写入开销** | **极低**：末尾顺序追加一行 JSON，零额外模型调用 | **中等**：需工具或后台 `memory-worker` 编辑文件、同步并重编译系统提示 | **高**：写入路径通常需调用 LLM 抽取事实、比对已有记忆决定增删改，并计算 Embedding | **低且确定**：每个超步（super-step）按序列化规则写库，纯工程 I/O，不耗费 LLM Token |
| **读取与进入模型方式** | `SessionManager` 沿当前活跃叶子回溯投影出整条分支消息链 | `system/` 文件直接编入 System Prompt（零检索延迟）；参考文件与旧对话按需读取／`recall` | 应用拿当前问题做相似度检索，拿到候选事实列表后再自行拼进本次提示词 | `checkpointer` 恢复图的内存通道值与 `next` 待执行节点队列，驱动引擎从断点续跑 |
| **Token 占用特征** | 随当前会话轮数线性膨胀，超长后必须靠窗口裁剪或摘要压缩兜底 | 常驻核心区占用固定比例的系统提示席位；参考区按需付费 | 与历史总库规模解耦，每次只为召回的 Top-K 条短事实买单 | 图状态本身留在宿主内存，只有显式放进消息通道的字段才消耗模型 Token |
| **典型失效模式** | 换个新会话就从零开始；切分支或长窗口压缩可能丢掉早期口头细节 | 什么琐事都往 `system/` 塞导致系统提示臃肿；模型自己改文件时误删旧规则；当前回合重编译滞后 | 抽取把玩笑或临时假设当真；提问措辞变化导致 Top-K 漏召回；新旧事实冲突未消解 | **只恢复图内变量，不撤销已发出的外部副作用**；错用内存 Saver 导致进程重启丢快照 |

### 1. 对话分支记录（Pi）：最忠实的“单次工作台黑匣子”

Pi 的会话管理不做任何自作聪明的事实提炼，而是把每一次用户提问、模型回复、工具调用和分支切换原原本本记进追加式 JSONL。它的杀手锏是**无损回溯与原地分叉**：当你让 Agent 尝试重构方案 A 走进死胡同时，可以直接把指针拨回分叉前的节点尝试方案 B——旧方案依然留在文件里备查，而新分支的上下文干干净净，绝不会被方案 A 的几千行失败报错污染。

但它的边界也同样清晰：**它管的是单场会话内的分支历史，不是跨月知识库**。你总不能在下个月开启第 100 个新会话时，把前 99 个会话的原始 JSONL 全塞进窗口。

### 2. 可编辑核心记忆文件（Letta Code）：像维护 `README` 一样维护长期默契

人类的工作搭档不会靠翻半年前的聊天记录来确认你的代码规范，而是把核心规范整理成一页置顶备忘录，每次变动就地修改。Letta Code 的 local MemFS v1 正是这个思路：把最关键、每次回答都必须遵守的身份认知与项目约定放进 `system/` 目录的 Markdown 文件里，直接编译进系统提示；把大块背景资料留在普通参考目录按需查阅。

它的优势是**确定性高、人类可读可手改**——打开 Markdown 就能直接审查甚至手动订正 Agent 的认知，不用去黑盒向量库里大海捞针。代价则是**席位珍贵且更新有编译周期**：`system/` 区寸土寸金，一旦塞满流水账就会挤爆工作预算；而且编辑文件后要经过同步与提示重编译，才会在后续回合生效。

### 3. 可检索原子事实库（Mem0）：用写入成本换海量跨会话扩展性

如果你的业务是面向十万终端用户的长期顾问或客服助手，每个用户一年下来散落着上千条碎片信息（用什么操作系统、对什么过敏、上次投诉过哪个订单），既装不进单次会话，也塞不进固定长度的 `system/` 文件。这时就需要 Mem0 代表的「**抽取—索引—按需检索**」范式。

注意 Mem0 开源同步路径里的两个关键工程事实：第一，它用**重写入换轻读取**——存的时候要把非结构化对话嚼碎成独立事实并消解冲突，这步本身就有延迟、Token 成本和抽取幻觉风险；第二，**检索只返回候选列表，不替你决定提示词怎么拼**——应用层拿到 Top-K 候选后，仍需自己控制注入位置、阈值过滤与预算上限。

### 4. 执行进度快照（LangGraph）：它是分布式状态机的存档点，不是聊天记忆！

这是全行业最常被误用的一类状态。LangGraph 的 `checkpointer` 保存的是 `StateSnapshot`——里面记着当前 `thread_id` 下各个状态通道的精确值、下一步等待唤醒的节点名（例如停在人工审批节点前）、待处理任务以及父快照指针。

它解决的是**容错续跑、人工介入挂起（Human-in-the-loop）与时间旅行调试**。千万记住一条铁律：**LangGraph 快照回滚的只是图引擎内部的内存状态，外部世界没有时光机**。如果第 3 步已经发出了邮件或触发了线上部署，你切回第 2 步的旧快照重开一条分支往下跑，只会把第 3 步再执行第二次！

## 架构选型决策指南：你的系统该选哪种（或怎样组合）？

别试图用一把锤子敲所有钉子。按下面的判断顺序做减法，往往能省掉一半过度设计：

1. **只需要单次任务内不断试错、支持回退换思路**？
   直接用**对话分支记录**（Pi 模式）配长会话压缩即可，不需要上向量库，也不需要复杂的后台记忆抽取。
2. **有一组跨会话必须 100% 稳定生效、体量在几千字以内的项目规范或个人偏好**？
   用**可编辑核心文件**（Letta `system/` 模式或项目级规则文件）直接编入常驻提示。千万别把这种“少而硬的铁律”丢进向量数据库赌 Top-K 召回率——一旦某轮提问没命中关键词漏召回，铁律就形同虚设。
3. **跨月沉淀的碎片事实成千上万，每次提问只用得上其中三五条背景**？
   再引入**可检索事实库**（Mem0 模式），作为常驻提示之外的“按需补充背景层”。
4. **任务跨度几十分钟甚至跨天，中间要挂起等人类点审批按钮，或者要求进程重启后从原节点续跑**？
   必须上**执行进度快照**（LangGraph Checkpointer 模式），并把测试用的内存 Saver 换成生产级持久化存储，同时为所有外部写操作配上幂等键。

在真实的生产级 Agent 系统里，最稳健的往往是**职责正交的组合拳**：例如用 **LangGraph 快照**兜底长流程的执行节点进度，用 **常驻核心文件**锁死绝不能忘的系统级红线，再用 **可检索事实库**按需捞取长尾历史背景——让每种状态待在它最擅长的那一层。
