# 请求超时后，先查结果，再决定是否重试

[返回对照章](../../docs/comparisons/permission-and-recovery.md) · [可编辑图源](scene.excalidraw) · [SVG](diagram.svg) · [PNG](preview.png)

假设助手要向一个服务发送操作请求，服务支持按预先约定的编号查询。发送前，助手先取得许可，分配并保存编号，图里用 `#42` 举例。这样即使回执丢了，仍有办法找原操作。

从左到右读上排：许可、发送、等待、超时，再按原编号查询。超时意味着这次连接没有及时带回结果。下排列出此时可能的情况：服务还没收到，请求还在路上，或服务已收到并正在排队、执行，甚至已经完成。虚线连接的是这些可能情况，具体是哪一种要靠查询分辨。

查到已完成，就记录原结果。查不到时，先看查询是否有延迟、旧请求是否还在途中。重试要满足服务的规则：可靠确认旧请求最终没有生效、以后也不会迟到，并且接口允许再次发送；或者服务支持在有效期内用同一个幂等键和相同参数安全重放。幂等键用于让服务识别“这是同一操作的再次请求”。条件不清楚时，记录“结果未知”，暂停并交给人核对。

下方说明中的 checkpoint 是程序保存的执行状态。它和工具状态、错误记录一起，帮助找回本地进度；已经发生的远端操作仍要向目标服务查询。

这是一张教学情境图。实际服务是否支持编号查询、幂等键，以及记录多久可查，需要单独核对。Codex、OpenHands、OpenCode、LangGraph 各自能提供哪些记录，见[对照章](../../docs/comparisons/permission-and-recovery.md)。
