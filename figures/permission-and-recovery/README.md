# 超时后，先对账，再决定是否重试

[返回对照章](../../docs/comparisons/permission-and-recovery.md) · [可编辑图源](scene.excalidraw) · [SVG](diagram.svg) · [PNG](preview.png)

这是一张**教学情境图**，不是 Codex、OpenHands、OpenCode 或 LangGraph 的共同内部架构。它只解释一次有外部副作用的动作在超时后，为什么不能把本地状态直接当成外部事实。

从左到右，操作者提出动作并准许发出，Agent 用稳定操作 ID（图中以 `#42` 举例）发出请求；连接超时后，本地只知道结果未知。请求可能未被接收、仍在传输，也可能已被接收而处于排队、执行或完成状态。虚线表示**尚未区分的可能世界**，不表示三条执行流都发生了，也不把“已接收”误写成“已完成”。下一步应按操作 ID 向目标系统查询；一次“查无记录”可能只是索引滞后，不能直接授权重试。只有目标服务给出可信的终态否定、能保证旧请求不再迟到，或支持用相同幂等键安全重放，才可考虑重试；否则保留未知并交人工核对。

最下方的边界说明：checkpoint、工具状态和错误事件能帮助定位本地进度，却不会撤销外部副作用。图中没有宣称目标系统一定支持幂等键、按 ID 查询或强一致状态；这些条件要由实际应用核对。四个系统各自能提供的局部证据及固定源码链接见[对照章](../../docs/comparisons/permission-and-recovery.md)。

`scene.excalidraw` 是规范图源；`build.py` 只重建规范图源，SVG/PNG 由 pinned Excalidraw 渲染器导出。图中没有固定版本元数据，版本与证据范围留在正文维护。
