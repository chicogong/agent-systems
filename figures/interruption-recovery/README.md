# 图的文字版：中断后先查询原操作

[返回章节](../../docs/concepts/interruption-recovery.md) · [可编辑图源](scene.excalidraw) · [SVG](diagram.svg) · [PNG](preview.png)

助手要创建一张工单，也就是记录待处理问题的任务单。应用先记下这次操作和业务标识 K，需要批准的动作先确认，再通过工具发送请求。正常收到结果时，就记录返回的工单 ID，接着处理后续工作。

图中竖向虚线标出的“副作用边界”，指请求从本地程序进入外部服务。跨过这条线后，服务可能已经创建工单。本地随后超时、取消或断线时，要回到外部服务查结果。

## 没收到结果，沿图中三条路判断

橙色“结果未知”指本地暂时拿不到可靠结果。“按 K / 请求 ID 对账”，用大白话说就是：拿着原操作的标识，查询服务实际做到了哪一步。

- **确认已创建：用原工单继续。** 取回已有工单 ID，走绿色路径，避免再建一张。
- **确认未创建，且可以安全重试：重新发送原请求。** 蓝色回路返回“发送创建请求”，沿用同一 K。`n` 是已重试次数，`N` 是预先设定的有限上限；只有 `n < N` 才继续，达到上限后交给人处理。
- **仍然未知：暂停自动操作。** 保留已有信息，走橙色“人工对账”路径，由人核对后决定继续、修正或补偿。

蓝色表示 Agent 侧动作，紫色表示进入外部服务的部分，橙色表示尚待核对，绿色表示已确认的结果。节点文字也给出了这些信息。

## 重试前要满足的条件

一次查询没有记录时，旧请求可能还在执行，或查询数据尚未更新。只有可靠确认旧请求已结束且没有生效，并确认接口允许安全重试，才考虑重发；另一种可重发的情况，是接口明确支持用原幂等键安全重放。幂等键是服务按约定识别同一次操作的标识，单独取个业务名字 K 并不能获得这项保证。

每次重试都要遵守接口约定的有效期，使用同一标识与同一组参数，并限制次数和截止时间。缺少可靠查询，也没有幂等保证时，保留“结果未知”，暂停自动重发。查询服务和人工核对都可能暂时得不到答案。

左侧的 `checkpoint`（检查点）是一条旁注：它保存图的执行状态。外部工单按服务的真实状态处理，恢复检查点后仍要核对已经发送的操作。

## 这张教学图依据什么

Pi 的固定提交 [`898ab804050730e9dcefb4443875d5a932aa6a32`](https://github.com/earendil-works/pi/tree/898ab804050730e9dcefb4443875d5a932aa6a32) 展示取消信号及 coding-agent 的模型错误重试；LangGraph 的固定提交 [`bdb85b5aa87a21de68371d2e534b81aeed398f57`](https://github.com/langchain-ai/langgraph/tree/bdb85b5aa87a21de68371d2e534b81aeed398f57) 展示检查点的选择和分叉。

查询工单、设计 K 和人工核对，是章节给应用的设计建议。图用于说明判断顺序，两个项目各自已有的能力及未验证内容见[章节](../../docs/concepts/interruption-recovery.md)。

运行 `python3 figures/interruption-recovery/build.py` 可重新生成原生 `.excalidraw`。用 `excalidraw-agent` 的固定渲染器从该图源导出 SVG 和 PNG；重新生成时须重查文本布局与裁切。
