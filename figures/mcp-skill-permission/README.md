# Skill、MCP 与许可边界图的文字版

这是一张教学抽象图，不是某个产品的内部实现或统一的审批顺序。图中实线表示一次获准任务的主路径，虚线表示影响或拒绝分支；颜色帮助区分角色，不代替箭头含义。

1. Skill 提供“先核对原文，再行动”的做事方法。它影响模型提案，但文本出现不表示相关工具已经运行。
2. 用户任务规定可读材料、可改范围和验收条件。MCP 的 `tools/list` 让宿主发现某个 Server 提供了 `kb.fetch` 等能力，宿主可以把相关能力呈现给模型；它不证明当前账户对某条资料有权限。
3. 模型提出“查文档”或“改文件”。宿主按照任务范围、工具配置和产品策略检查、路由；必要时取得用户批准。拒绝分支表示动作未执行，不能写成“已经改好”。
4. 获准后工具才实际读取远端知识库或编辑本地文件。`tools/call` 的返回是这次调用的结果，还需区分错误、缺失和可疑外部内容。
5. 最后对照原任务核对知识库原文、文件 diff 和测试记录；调用成功本身不是整个任务的验收。

图中 `kb.fetch` 是书中的假设工具名；MCP 规定工具发现与调用结构，不规定该工具或统一的产品审批 UI。详见[正文](../../docs/concepts/mcp-skill-tool-lifecycle.md)及其[来源台账](../../sources/mcp-skill-tool-lifecycle.md)。
