# 图的文字版：给几个助手分工，再检查合并

[返回章节](../../docs/concepts/delegation-and-handoff.md) · [可编辑图源](scene.excalidraw) · [SVG](diagram.svg) · [PNG](preview.png)

准备一场读书会，可以让助手 A 整理时间、B 核对场地，再由协调者把结果合起来。图从左到右说明：任务怎样交出去、结果怎样收回来、最后由谁确认完成。

## 正常分工怎样走

1. **提出任务的人先说清要求。** 图中的“任务负责人”说明目标、完成标准，以及由谁确认完成。
2. **协调者列出每份工作的要求。** “分工清单”写明任务 ID、采用哪版材料、处理范围、允许动作，以及需要交回什么。A 和 B 各拿到自己需要的输入，只在允许范围内工作。
3. **助手把结果和依据一起交回。** “状态 + 依据”表示完成了哪些内容、引用哪些原文；“外部操作与未知项”包括已经发生的写入、发送等操作，以及还未确认的信息。
4. **协调者检查两份结果。** “汇总并核对”包括核对材料版本、缺失信息、互相矛盾的说法和已经发生的动作。比如时间来自旧通知、场地来自新通知，就先回到原文查版本。
5. **按原要求确认完成。** 结果有足够依据、满足原目标时，由任务负责人或其明确授权的人、检查规则决定是否交付。

## 有缺口时，沿虚线回去补

虚线从最后检查回到任务清单，表示先重新确认输入、范围、权限和返回要求，再补充依据、重新派发或交给人处理。需要写文件或调用外部服务的任务，重新执行前还要查明原动作是否已完成，按授权范围和接口约定决定是否适合重试。

颜色区分任务安排、A / B 的工作和最后检查；箭头方向与文字说明了各份信息送到哪里。

## 图与代码例子各说明什么

这是应用可以采用的协作设计。正文中的 LangGraph `Send` 示例展示两步：把特定输入发给节点，再通过 `reducer`（合并状态更新的规则）收集结果。任务要求、权限检查、冲突处理和最终交付，还需要由应用安排。

图省略了调度时间顺序、存储、具体工具与协议。固定源码、核对日期和运行验证范围见[正文](../../docs/concepts/delegation-and-handoff.md)。
