# 前缀缓存（KV Cache）经济学：前段稳如磐石，变化留在队尾

[返回前缀缓存章节](../../docs/concepts/cache-and-cost-economics.md) · [图源](scene.excalidraw) · [原尺寸 SVG（手机可放大）](diagram.svg) · [PNG](preview.png)

在动辄连续运行几十步工具调用的 Agent 循环里，输入 Token 往往是输出 Token 的数十倍。推理引擎依靠精确前缀匹配复用历史注意力键值（KV Cache），一旦拼装顺序不当，成本与延迟会相差一个数量级：

1. **上方红色反模式（前缀突变导致 0% 缓存命中）**：在系统提示开头写入每秒变化的动态时间戳、每轮按场景动态删改顶层 `tools` Schema 列表，或者采用“进一条新消息就踢掉第 1 条老消息”的逐条滑动窗口。这三种做法都会破坏前缀字节一致性，迫使模型把后面几万字历史从头重算一遍。
2. **下方绿色工程正道（高命中只追加布局）**：按“稳定度从高到低”依次排布请求体——最前面放**静态系统指令与固定排序的工具定义**（需要临时禁用某工具时在宿主执行门拦截，而非篡改前缀声明），接着放**仓库级规则与阶段压缩摘要**，中间保持**纯追加、不原地涂改的对话历史**，最后只在**队尾**追加本轮最新工具观察与动态提醒。
3. **周期性水位线压缩**：平时几十步保持纯追加吃满 90%+ 缓存复用；只有总长度逼近上下文水位线时，才集中做一次分段摘要压缩，在可预期的单次重建后开启下一轮稳定缓存周期。
